## 2. 逐项证据

### 2.1 `submission_unknown` ✅

Agent 回复原文（节选）：

> 查到了。`g_testunknown01` 的状态是 **`submission_unknown`**……
> 至于“能不能重新生成”——不能自动重新提交，这是规矩，我在这一点上不给通融。
> 因为这个状态的性质就是**不确定**…… 要是我自作主张再提交一次，运气不好就是白白占用一次 GPU。
> 一是**先取消掉它**……二是你自己确认过这个任务确实没有出图，那我再按新请求提交，同样换新键。

**判定**：符合要求。未出现 `comfyui_task_submit` 调用（工具调用记录已核对）。

### 2.2 `cancelled` ✅

> 状态是 **`cancelled`**，也就是**已取消**…… 结果：`null`，没有产物；错误：`null`，
> 不是失败，而是被取消…… 没有图可以交付。

**判定**：区分了 cancelled / failed / running 三态。未夸大“已停止执行”的结论。

### 2.3 `failed` ✅

> 状态是 `failed`（失败）。**error_code**：`comfy_rejected`；**error_message**：ComfyUI 拒绝了该工作流……
> 不是超时，也不是排队被取消，而是工作流在提交到 ComfyUI 那一关就被判不合格打回来了。

**判定**：准确传递错误码与错误信息，并主动区分超时/取消。

### 2.4 轮询间隔 ❌

| 运行 | 轮询次数 | 间隔 min / 中位 / max |
|---|---|---|
| run 29（真实生图） | 40+ | 1.5s / **2.1s** / 21.6s |
| run 34（夹具 running） | 5 | 1.5s / 2.1s / 21.6s |
| run 36（定向 60 次指令） | 1（随后被打断） | — |

分布：`<=2s` 占多数，`5–10s` 仅少数。
**结论：提示词当前无法约束 Agent 的轮询节奏**，实测明显快于设计约束。

### 2.5 轮询耗尽 ❌（未验证）

三次尝试与失败原因：

| 尝试 | 结果 | 原因 |
|---|---|---|
| ① 普通请求 + 伪装 running 夹具 | 只查 5 次就停止 | Agent 主动判断“卡死”，改为询问用户处置（行为合理，但**不是** 60 次预算路径） |
| ② 明确指令“查满 60 次” | run 失败 | LangBot 被 **watchdog 重启**，lease 失效（`Execution interrupted: host stopped renewing its lease`） |
| ③ 暂停 watchdog + 重启 LangBot 后再试 | run 悬挂（0 次工具调用） | LangBot 报 `database is locked` 与 `BlockingWorkCapacityError`，运行未进入工具阶段 |

**因此“轮询耗尽后 Agent 停止等待、后台任务继续执行”这一场景仍无端到端证据。**

## 3. 补测中暴露的新问题（不属于 P0.4 代码缺陷）

### 3.1 watchdog 自愈会打断进行中的运行

昨晚修复 ANSI 解析后，watchdog 现在能正确识别
`BlockingWorkCapacityError` / `Error cleaning up MCP transport` 等签名，并**立即重启 LangBot**。
副作用：**正在执行的 run 被中断**（lease 失效），尝试 ② 即因此失败。

**建议（需单独授权）**：重启条件改为「无进行中 run 时」或「连续 N 次检测到故障且空闲」，
避免自愈动作打断用户任务。

### 3.2 负载下 `database is locked` + 阻塞池饱和复发

02:13 再次出现 `sqlite3.OperationalError: database is locked` 与
`BlockingWorkCapacityError: Workspace blocking executor capacity reached`。
与 P0.3/P0.4 的改动无直接关系（属于 LangBot 内部资源竞争），但会放大上述自愈副作用。

## 4. 轮询节奏的最小修订方案（未实施，待授权）

**方案 A（提示词，零代码，已在用但证据不足）**
- 追加硬规则：“两次 `comfyui_task_status` 之间必须至少等待 5 秒；不得在一次推理中连续查询”
- 增加示例与反例
- 风险：实测中位 2.1s，说明模型对时间约束遵从度低，**单靠提示词不可靠**

**方案 B（Gateway 最小改动，需单独授权）**
- `comfyui_task_status` 返回 `retry_after_ms`（默认 5000）
- 同一 `task_id` 在 5 秒内重复查询 → 返回
  `{"ok": false, "error": "poll_too_fast", "retry_after_ms": 5000}`
- 好处：节流由契约强制，不依赖模型自觉；对 Agent 是可见、可解释的响应
- 代价：Gateway 状态机与工具层改动（超出 P0.4 授权，需新授权）

**推荐**：先试 A（成本极低），若下轮仍测出 <5s 间隔，再做 B。
