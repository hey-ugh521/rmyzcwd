**B 的实现要点**

- 状态：进程内 `_poll_state`（不落库、不改任务状态机）
- 首次查询放行；距上次**有效**查询 < 5s → 返回
  `{"ok": false, "error": "poll_too_fast", "task_id", "retry_after_ms", "interval_ms", "valid_queries", "attempted_queries"}`
- **被拒绝的查询不更新 `last_valid`**（等待窗口不会越推越远）
- 终态任务（completed/failed/cancelled）**立即放行**
- 全程无 `sleep`
- 每次查询记录 `attempts` 与 `valid` 两个计数，拒绝时写 WARNING 日志

**A 的规则要点**：有效查询间隔 ≥5s（优先 5–10s）；收到 `poll_too_fast` 必须按 `retry_after_ms` 等待；被拒查询不计入 60 次预算；终态可立即读。

## 3. 第二层：真实环境验证

请求「画一张雨夜里的猫，竖版」，run 38 结果：

| 指标 | 数值 |
|---|---|
| 运行结果 | **completed**（image 已交付） |
| 总耗时 | 298 秒（含冷启动） |
| `comfyui_task_status` 调用（尝试） | **57 次** |
| 其中被限流拒绝 `poll_too_fast` | **28 次**（49%） |
| 网关内部有效查询计数 | 约 27 次 / 298 秒（≈11 秒一次） |
| 调用级间隔 | min 1.1s / 中位 3.2s / max 48.4s |

网关日志样例：

```
WARNING poll_too_fast task=g_aa365a07 since=2.79s retry=2214ms (valid=26 attempts=51)
WARNING poll_too_fast task=g_aa365a07 since=4.30s retry=702ms  (valid=26 attempts=52)
WARNING poll_too_fast task=g_aa365a07 since=1.78s retry=3223ms (valid=27 attempts=54)
```

**解读**：Agent 原始调用频率仍然偏快（A 的约束力有限，57 次调用），
但 **B 把「有效查询」频率钳制在 ≥5s**（57 次调用只放行 27 次有效），
即协议层已保证节奏约束，不再依赖模型自觉。
